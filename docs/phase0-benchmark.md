# Phase 0 benchmark: in-browser recognition (2026-11-09)

Machine: Apple M4 Pro, macOS, Node v26.13.0. Models: Beat This! small0 (4.92 MB, MIT) and BTC large-voca
(6.47 MB, MIT per upstream; one redistributor says CC-BY-NC-SA 4.0), see README "Models". Command:
`npm run bench` (onnxruntime-node CPU), `npm run bench -- --runtime web` (onnxruntime-web WASM, 1 thread, in
Node), and the extension bench page `bench.html` run in Playwright's Chromium 158 headless shell with the
`dist/` extension loaded (WebGPU for the beat model, WASM for chords). Raw JSON: `bench-out/` (gitignored).

## Data

24 synthetic clips, 825 s total, generated by `src/bench/synth.ts` at 48 kHz and resampled to 22.05 kHz like
the capture path: tempos 72/96/120/150, 4/4 and 3/4, piano / strummed guitar / pad / e-piano, close /
inverted / guitar-like voicings, drums on half, bass on two thirds, white noise at 20 dB or 10 dB SNR on half,
chords maj, m, 7, maj7, m7, sus2, sus4 from 10 common progressions, some half-bar changes.

## Speed

Real-time factor = processing seconds / audio seconds (lower is faster), whole-clip analysis.

| Stage | Node CPU | WASM in Node (1 thread) | Browser (beat WebGPU, chords WASM) |
|---|---|---|---|
| Resample 48→22.05 kHz | 0.0027 | 0.0025 | 0.0107 |
| Features (log-mel + CQT, TS) | 0.0098 | 0.0089 | 0.0243 |
| Beat This! | 0.0111 | 0.0908 | 0.0063 |
| BTC | 0.0009 | 0.0029 | 0.0033 |
| Total | 0.0244 | 0.1051 | 0.0447 |

Per-call latency (median of 10): Beat This! on one 1500-frame (30 s) window: 263 ms CPU, 1605 ms WASM,
101 ms WebGPU (p90 119). BTC on one 108-frame (10 s) window: 8.5 ms CPU, 17.0 ms WASM, 18.4 ms browser.
CQT extraction: 1191–1279 frames/s in Node, 505 frames/s in the browser bench (live needs 10.8 frames/s).

Live "인식 중" latency is about CQT look-ahead 0.74 s + up to 0.5 s update interval + ~17 ms model.
With WASM only, a full 4-minute song would need ~13 s of beat inference at the end; listening mode instead
runs each 30 s beat chunk as soon as it is complete, so only the last chunk remains after the song ends.

## Accuracy (synthetic)

| Metric | Node CPU | WASM | Browser (WebGPU beats) |
|---|---|---|---|
| WCSR majmin | 97.05 % | 97.05 % | 95.61 % |
| WCSR root | 95.15 % | 95.15 % | 93.59 % |
| WCSR sevenths | 90.05 % | 90.05 % | 88.59 % |
| Beat F (±70 ms) | 0.838 | 0.838 | 0.818 |
| Downbeat F | 0.890 | 0.890 | 0.799 |
| Tempo within 4 % | 62.5 % | 62.5 % | – |
| Meter correct | 66.7 % | 66.7 % | – |

Beat F uses a maximum one-to-one matching within ±70 ms (fixed after review; the first run used greedy
nearest matching). Rerunning `npm run bench` and `npm run bench -- --runtime web` with the fix gave the same
numbers to all printed digits (beat F 0.8378972468992273, downbeat F 0.8897616468574271 in both). The browser
column was not rerun and still comes from the greedy matcher.

Ablations (majmin, Node): frame-wise argmax without beat sync 96.46 %; Viterbi on fixed 0.5 s units without
beats 89.38 %; BTC 25-class majmin model with the same pipeline 97.05 %. Beat-synchronous smoothing adds
about 0.6 points over frame argmax; using beats instead of fixed units adds about 7.7 points.

## Caveats (read before trusting the numbers)

- Synthetic audio is not real music: no vocals, mixing, reverb, tuning drift or expressive timing. Expect real
  songs to score lower; the 20-song real evaluation (checklist D, chart-vs-chart agreement in the panel and
  `npm run bench -- --compare`) is the real test.
- Tempo errors are mostly half-tempo on clips without drums (e.g. 96 → 48, 150 → 75 BPM). Beat F 0.65 on those.
- Root errors on sus chords are partly label ambiguity: Gsus4 and Csus2 have the same notes.
- WebGPU gave lower beat/downbeat F than WASM on the same clips, so listening mode uses WASM by default
  (`USE_WEBGPU` in `src/extension/offscreen/listen.ts`). Not investigated further.
- CQT features are a TypeScript re-implementation; against librosa 0.10.2 (`scripts/verify-features.py`) the
  mean |Δ log| is 0.089 with no per-octave bias, larger only in near-silent bins. BTC was trained with older
  librosa.
- The capture-to-timeline latency is a fixed 50 ms guess; tab capture itself was not exercised headless.
- Timings come from one machine and one run; the browser numbers are a headless shell.
