# Vibe Guitar 구현 제안 (2026-11-09, 자문 반영본)

## 사용 범위 (2026-11-09 사용자 결정)
- 상업 배포 없이 사용자 본인만 쓰는 개인용 도구다. 웹 스토어 등록, 공유 캐시 배포, 출판사 권리 문제는 범위 밖이다.
- 따라서 8장의 법률·라이선스 항목은 공개 배포를 다시 검토할 때만 다룬다. 비상업 라이선스 모델도 후보에 넣을 수 있다.
- "공유 캐시"는 본인 기기의 로컬 코드표 저장소로 대체한다. 오디오를 외부로 보내지 않는 원칙은 유지한다.

## 진행 상황 (2026-11-15)
7장 로드맵의 각 항목이 지금 어떤 상태인지 README.md와 docs/phase0-evidence.md만을 근거로 정리한다. 상태는 "프로토타입에 구현됨, 실사용 검증 전", "확인됨", "사용자 확인 대기", "보류" 가운데 하나로 적는다. 괄호 안의 기호는 docs/phase0-evidence.md의 행 번호다.
- 0단계, 코드표로 편곡 엔진과 따라 치기 화면 만들기: 프로토타입에 구현됨, 실사용 검증 전. 직접 만든 코드표 대신 공개 주석으로 만든 연습용 코드표 네 곡을 쓰며, 사용자가 실제로 쳐 보는 시험은 아직 하지 않았다(C1~C12).
- 0단계, 탭 캡처 확인: YouTube는 확인됨이다. 오디오가 들어오고, 평가용 캡처도 100번 넘게 성공했다(B1). YouTube Music 캡처는 기록이 없어 사용자 확인 대기다(B2). Apple Music 웹은 한 번의 가능성 확인을 남겨 두어 사용자 확인 대기다(B5).
- 0단계, 브라우저 안 모델 속도·메모리와 시각 보정 오차 측정: 확인됨. 지연 측정으로 캡처 위치 상수를 정했고, 2026-11-15 재측정 뒤 0.069초를 쓴다(N2). 다만 듣는 동안의 CPU 사용률과 소리 끊김 여부는 아직 기록되지 않았다(D11).
- 0단계, 20곡 체감 정확도 평가: 확인됨. 사용자가 귀로 판단하는 방식 대신 공개 주석과 비교하는 평가로 바꾸어 진행했다(N13).
- 1단계 MVP(YouTube·YouTube Music 어댑터, 듣기 모드 뒤 따라 치기, 공유 캐시 대신 로컬 코드표 저장소, 네 단계 편곡 난이도, 사용자 코드 수정): 프로토타입에 구현됨, 실사용 검증 전. 사용자의 실사용 시험(Linear VGT-5)을 아직 하지 않았다.
- 2단계, 휴대폰 악보대와 구간 반복·속도 조절: 프로토타입에 구현됨, 실사용 검증 전. 실사용 시험(VGT-5)에서 함께 확인한다.
- 2단계, Apple Music 웹: 사용자 확인 대기. 가능성 확인(B5)에서 소리가 들리는데도 오디오가 들어오지 않으면 지원하지 않는다.
- 3단계, Android·iOS 앱(VGT-10): 보류. 아직 시작하지 않았고, VGT-5가 끝나도 자동으로 시작하지 않는다. 실사용에서 휴대폰 악보대로 할 수 없는 일이 드러나면 사용자가 시작 여부를 정한다.
- 코드 인식 개선: 한 차례 개선을 반영했다(VGT-18, N1, PR #37). 오류 유형별 추가 개선과 미세 조정은 새 평가 자료가 생기거나 사용자가 결정할 때까지 보류한다.

3장, 7장, 8장에 남아 있는 "공유 캐시" 언급은 2026-11-09에 정한 로컬 코드표 저장소 결정으로 대체되었다. 그 절들은 당시 기록으로 남겨 두고 고쳐 쓰지 않는다.

## 0. 결론
- 만들 수 있다. 다만 세 부분의 난이도가 크게 다르다.
  - 재생 위치 동기화: 데스크톱 브라우저의 YouTube·YouTube Music에서는 비교적 쉽다. Apple Music 웹은 검증이 필요하고, 모바일은 제약이 크다.
  - 코드 인식: 공개 모델로 구현할 수 있지만 정확도와 실시간성에 한계가 있다. 이미 작은 크롬 확장들이 하고 있으므로 차별점이 되지 못한다.
  - 숙련도별 편곡과 연습 화면: 확실히 구현할 수 있고, 경쟁 제품이 약한 영역이다. 이 부분이 핵심 차별점이다.
- 추천 첫 제품: 데스크톱 크롬 확장(YouTube·YouTube Music 우선) + 휴대폰 보조 화면.
- 가장 중요한 설계 원칙: 따라 치기에는 "다음 코드 미리 보기"가 필요하다. 실시간 인식만으로는 이를 제공할 수 없으므로 "듣기 모드"와 "따라 치기 모드"를 나눈다.

## 1. 시장 현황 (2026-11 웹 조사)
| 제품 | 하는 일 | 빈틈 |
|---|---|---|
| Chordify | YouTube 링크 분석, 코드 타임라인, 가사 동기(2023), 마이크 실시간 인식 | 자기 사이트에서 재생해야 함 |
| Moises | 코드 인식, easy/medium/advanced 보기, 카포 모드 | 곡을 앱으로 가져와야 함, 무료는 첫 1분 |
| Chord ai | 파일·YouTube·마이크 실시간 인식 | 편곡·연습 기능 약함 |
| Ultimate Guitar "Instant Chords: Tab Connect" 확장 | Spotify·YouTube·YouTube Music 웹에서 재생 중인 곡의 악보 검색 | 사람이 쓴 악보로 이동만 함, 재생 동기 없음 |
| 실시간 인식 크롬 확장들(Real-time Chord Recognition 약 1천 명, Chord Finder 약 3천 명 등) | 탭 오디오에서 코드를 실시간 표시 | 소규모, 편곡·숙련도 기능 없음 |
| Spotify 공식 기능 | 확인되지 않음(커뮤니티 요청만 존재) | |

결론: "코드를 보여 준다"는 이미 있다. "내 플레이어에서, 내 실력에 맞는, 실제로 칠 수 있는 편곡을, 미리 보면서 따라 친다"는 조합은 찾지 못했다.

## 2. 플랫폼별 가능성
| 플랫폼 | 곡·재생 위치 | 오디오 | 판단 |
|---|---|---|---|
| 크롬 확장 + 웹 플레이어 | 사이트별 어댑터로 media element의 currentTime, 곡 ID 읽기 | tabCapture. 사용자가 확장을 한 번 눌러야 시작(공식 문서 확인), 같은 탭에서는 페이지 이동 후에도 유지 | 1순위 |
| Apple Music 웹 | MusicKit JS 내부 audio 요소(비공식 경로) | DRM(Widevine) 오디오가 캡처되는지 미확인. 안 되면 지원하지 않음(우회 금지) | 검증 후 |
| iOS 앱 | Apple Music 앱만 systemMusicPlayer로 곡·위치 조회(폴링) | 다른 앱 오디오 불가, 마이크만 | 3단계 |
| Android 앱 | 알림 접근 권한 + MediaSessionManager로 대부분 플레이어 조회 | AudioPlaybackCapture는 앱이 거부 가능, YouTube 계열이 막는다는 비공식 보고 | 3단계 |
| 웹 연습 플레이어(공식 YouTube 임베드) | IFrame API로 위치·탐색·속도 제어 | 분석에는 쓰지 않음, 미리 준비된 코드표만 재생 | 0단계 검증·연습 페이지용 |

## 3. 핵심 설계: 두 모드
- 듣기 모드(코드표가 없는 곡의 첫 재생)
  - 현재 코드를 "인식 중" 표시와 함께 보여 준다. 따라 치기용이 아니라 "이 코드가 뭐지?" 확인용이다.
  - 곡을 끝까지 들으면 정밀 분석(앞뒤 문맥을 모두 쓰는 모델)으로 완전한 코드표를 만든다.
- 따라 치기 모드(완성된 코드표가 있는 곡)
  - 다음 코드를 최소 1마디 전에 보여 주고, 카운트인, 구간 반복, 미리 보기 시간 조절을 제공한다.
- 공유 캐시
  - 끝까지 분석된 코드표만 "정확한 녹음 ID"(YouTube videoId 등) 단위로 공유한다. 일부만 들은 결과는 공유하지 않는다.
  - 다른 업로드·다른 서비스 사이의 정렬은 초기에 하지 않는다(인트로·편집 차이로 단순 오프셋이 맞지 않는다).
  - 인기 곡은 다른 사용자가 이미 분석해 두었으므로 첫 재생부터 따라 치기가 가능해진다.

## 4. 구성 요소
1. 플레이어 어댑터(사이트별): 곡 ID, 제목·아티스트, 재생 위치, 재생·정지·탐색·광고 감지. 필요하면 페이지 본 컨텍스트에 스크립트를 주입한다.
2. 오디오 캡처: 서비스 워커에서 getMediaStreamId → 오프스크린 문서에서 getUserMedia. 캡처 중에는 탭 소리가 꺼지므로 AudioContext로 다시 출력한다.
3. 시각 보정: 캡처 샘플 시각, 분석 창, 재생 시각, 실제 출력 지연이 서로 다르다. 탐색·버퍼링·속도 변경 때마다 다시 맞춘다.
4. 분석(브라우저 내부, 오디오 외부 전송 없음)
   - 실시간 경량 모델: 현재 코드.
   - 정밀 모델: 박자·다운비트(Beat This! 등), 코드(BTC·ChordFormer 계열), 조성. 실시간 동작 여부, 메모리, 속도는 스파이크에서 측정한다.
5. 코드표 데이터 형식(핵심 인터페이스): 녹음 ID, 박자표·마디 격자, 코드 이벤트(시작 시각, 코드, 신뢰도), 분석 범위, 출처(자동·사용자 수정·직접 작성). 인식기, 직접 작성, 커뮤니티 수정이 모두 같은 형식을 쓴다.
6. 편곡 엔진(5장).
7. 화면: Chrome Side Panel + 휴대폰 보조 화면(QR 연결, WebSocket 동기화).

## 5. 편곡 엔진 (자문으로 수정한 부분 포함)
- 운지 변경과 화음 대체를 구분해서 표시한다.
  - 운지 변경(같은 화음, 쉬운 모양): F 바레 → 작은 F(xx3211), Bm 바레 → 작은 Bm(xx4432).
  - 화음 대체(소리가 달라짐, "대체" 표시): F → Fmaj7(xx3210), Bm → Bm7(x20202), Cmaj7 → C, Dm9 → Dm.
- 간소화는 문맥을 본다. sus 코드나 슬래시 베이스가 곡의 흐름을 만들면 유지한다. 빠른 코드 변화의 병합은 박자 정보를 근거로 한다.
- 카포는 소리 나는 키를 유지한 채 손 모양만 바꾼다. 실제 소리 나는 코드와 손 모양을 함께 표시한다(예: 소리 A♭ / 카포 1 + G 모양). 카포로도 모든 코드가 쉬워지지는 않는다.
- 개인화: 잡을 수 있는 코드 목록, 코드 전환 속도, 곡 템포, 손 뻗기, 편한 카포 범위를 비용 함수에 넣고, 곡 전체를 한 번에 최적화(DP)한다. 정적인 운지 난이도만으로 판단하지 않는다.
- 주법: 박자표와 셔플 감각을 먼저 판정한 뒤 패턴을 고른다. 원곡 기타 파트를 그대로 복원한 것이 아니므로 "추천 반주"로 표시한다.
- 단계 예시
  - 입문: 운지 변경 우선, 필요한 경우에만 화음 대체(표시), 카포 추천, 박마다 다운 스트로크.
  - 초급: 7th 허용, D-DU 계열 패턴.
  - 중급: 원곡 코드와 바레, 8비트 패턴.
  - 상급: 텐션·슬래시 보이싱, 아르페지오·핑거스타일 제안.

## 6. 첫 사용 경험
튜닝·카포 안내 → 이 곡에 나오는 코드 미리 보기 → 어려운 전환만 따로 연습 → 카운트인 후 따라 치기.
신뢰도가 낮은 구간은 "불확실"로 표시하고, 운지 그림을 빠르게 바꾸지 않는다.

## 7. 로드맵
- 0단계(1~2주): 핵심 가치 검증과 기술 스파이크를 동시에 진행
  - 직접 만든 코드표 3~5곡으로 편곡 엔진과 따라 치기 화면을 만들고, 실제로 쳐 본다.
  - 탭 캡처: YouTube·YouTube Music, Apple Music 웹(DRM 포함) 오디오가 실제로 들어오는지 확인.
  - 브라우저 내 모델 속도·메모리, 시각 보정 오차 측정. 가요·팝·어쿠스틱 20곡 체감 정확도 평가.
- 1단계 MVP: YouTube·YouTube Music, 듣기 → 따라 치기, 공유 캐시(끝까지 분석된 것만), 편곡 2~3단계, 사용자 수정.
- 2단계: Apple Music 웹(캡처 가능 시), 휴대폰 보조 화면, 구간 반복·속도 조절.
- 3단계: Android(미디어 세션 + 마이크), iOS(Apple Music 재생 위치 + 마이크).

## 8. 리스크와 법률 검토 항목
- 정확도: 장·단3화음 수준은 비교적 정확하지만 확장 화음은 아직 어렵다. 가요의 복잡한 화성에서 오류가 날 수 있다. 신뢰도 표시와 사용자 수정으로 보완한다.
- 약관·권리(법률 검토 필요): 각 플랫폼 약관에서 탭 오디오 분석이 허용되는지, 자동 생성 코드표를 공유 캐시로 배포할 때의 권리, 크롬 웹 스토어 정책, 가사 표시(라이선스 필요, MVP 제외). "오디오를 업로드하지 않는다"만으로 준수가 증명되지는 않는다.
- 모델·데이터 라이선스: 코드, 가중치, 학습 데이터, 운지 DB를 각각 확인한다.
- 경쟁: 1장의 제품들. 사용자가 "칠 수 있는 편곡과 미리 보기" 때문에 옮겨 올지는 0단계에서 확인한다.

## 9. 검토했지만 주 제품으로 고르지 않은 대안
- 웹 연습 플레이어 + 직접 준비한 코드표(자문 제안): 첫 재생부터 완벽하지만, 곡 수가 작성량에 묶이고, 유명 곡 코드표를 배포하려면 출판사 허락이 필요할 수 있다. 사용자님의 요구("내 플레이어에서 아무 곡이나")와도 다르다. 0단계 검증과 연습 페이지로만 쓴다.
- 링크 붙여넣기 + 서버 분석: 원본을 내려받아야 하므로 약관 위험과 서버 비용이 생긴다.
- 모바일 우선: 다른 앱의 오디오·재생 위치 접근이 막혀 있어 첫 제품으로 부적합하다.
